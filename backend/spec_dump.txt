1. Summary and decisions so far
The goal is to turn SceneCraft from a single-user analysis tool into a Wattpad-style platform. Writers publish a book as
one manuscript document with a cover image. Readers browse a catalogue, read page by page and use SceneCraft's
analysis features on the book they are reading. Publishers read the book, see a condensed view of the analysis and
send the writer a publishing request. Admins watch platform health. The existing 10-stage BullMQ pipeline, workers,
models, graph and charts stay; a product layer is added on top.
TopicDecision
RolesFour roles with RBAC: admin, writer, reader, publisher. Admin is seeded, never self-signup. Publishers
apply and are approved by an admin before they can send requests.
Publishing formatWriter uploads one manuscript (PDF, DOCX or TXT) plus a cover image. No chapter-by-chapter
publishing in v1.
Reading experienceSingle document read page by page, like Google Play Books: page turns, scrubber, resume where you
stopped, font and theme settings.
SceneCraft featuresReaders get the analysis tabs on every book. Publishers get a lighter, read-only pitch view. Continuity
Checker stays writer-only.
Writer templatesWriter chooses one of 3 layouts for how their book page looks to readers (Classic, Showcase, Notebook)
plus an accent colour.
Publisher flowBrowse and read, star a book to a wishlist, click "I want to publish" and fill a details form. The writer gets a
request, accepts or declines, and chat opens on acceptance.
LoginEmail and password only for now. A Google sign-in slot is reserved in the UI.
Image storageCloudinary for covers and avatars. MongoDB stores only the publicId and URL. Manuscript files stay
private (section 8).
Look and feelLayout, flow and colour family follow Wattpad (orange primary, white surfaces, cover-led grids). Logo is
yours. Copy, illustrations and covers are original (section 12).
CopyrightRights checkbox on publish, Report button, admin queue, strikes and takedown page (section 13).
Scope note. This document is a build brief, not legal advice. Have a lawyer review the Terms, Privacy Policy and
takedown text before the platform goes public.

4. The page-by-page reader
Readers should feel like they are turning pages in one continuous document, similar to Google Play Books, instead of
jumping between chapters. SceneCraft already parses the manuscript to text and stores scene offsets, so the cleanest
approach is to paginate that text once on the server and reuse the offsets everywhere.
How pagination works
1
On upload, store the original file in GridFS (so the writer can re-download it) and parse it with the existing pdf-parse,
mammoth or plain-text parser.
2
A new paginator service splits the clean text into pages of roughly 1,800 characters, breaking only at paragraph or
sentence boundaries. Store pageOffsets[] (start index of each page) on the Book.
3
To find which page a scene or character mention is on, binary-search pageOffsets with its stored offset. This
powers spoiler filtering, scene ticks on the scrubber and "jump to scene".
4
Pages are served in small windows (for example pages 10 to 14) so the client never downloads the whole book at
once.
Why not render the original PDF? A PDF viewer keeps the original layout but cannot reflow for phones, cannot change
font size and makes offset-to-page mapping harder. Text pages are consistent with your analysis offsets. If a writer needs
exact layout (poetry, illustrated books) you can add an optional "original PDF mode" with pdf.js later.

8. Images with Cloudinary
Cloudinary is a good fit for covers and avatars. It stores the image, resizes and compresses it through the delivery
URL, and serves it from a CDN. That replaces the resize step, the image-serving route and the cache headers that a
MongoDB-based approach would need.
PieceApproach
What MongoDB stores
Only publicId and url (the secure_url Cloudinary returns) on the Book (cover) and User (avatar).
Never the image bytes.
Upload path (recommended for
v1)
Browser sends the file to your API with multer (memory storage). The API checks role, type and
size, then calls cloudinary.uploader.upload_stream and saves the publicId and url. Simple, and
nothing reaches Cloudinary without passing your checks.
Later option
Signed direct upload from the browser: your API issues a short-lived signature and the browser
uploads straight to Cloudinary. Saves server bandwidth; add it only if uploads become heavy.
Folders
platform/covers and platform/avatars, so you can find and clean up assets in the Cloudinary
console.
Sizes through the URL
Cover on the book page: c_fill,w_600,h_900,f_auto,q_auto. Grid thumbnail:
c_fill,w_200,h_300,f_auto,q_auto. Avatar: c_fill,w_256,h_256,g_face,f_auto,q_auto. Build URLs
from the publicId in one helper (for example coverUrl(publicId, "thumb")) so sizes can change later
without touching stored data.
Replacing and deletingCall cloudinary.uploader.destroy(publicId) when a cover is replaced or a book is deleted, so unused
images do not pile up.
ValidationAccept JPEG, PNG and WebP only. Cap the file at about 5 MB in multer, before anything is sent to
Cloudinary.
Config
Install cloudinary and multer in backend. Add CLOUDINARY_CLOUD_NAME,
CLOUDINARY_API_KEY and CLOUDINARY_API_SECRET to backend/.env. The API secret never
goes to the frontend.
Keep manuscripts off public Cloudinary URLs. Cloudinary delivery URLs are public by default. Covers are meant to be
public, but the uploaded PDF, DOCX or TXT is the writer's work, sometimes unpublished. Keep the original file in
MongoDB GridFS (or behind private, authenticated delivery) and store the parsed text and page offsets in MongoDB. Only
covers and avatars go to Cloudinary.
Check the plan limits. Cloudinary's free plan caps monthly storage, transformations and bandwidth, and limits file sizes. I
have not verified the current numbers, so check Cloudinary's pricing page before launch. Using f_auto and q_auto and
small grid thumbnails keeps usage low.
Keep it behind one service
Put all Cloudinary calls in storage.service.js with three functions: saveImage, deleteImage and imageUrl. Controllers
never call Cloudinary directly, so moving to another provider later means changing one file.
Cover upload checklist
•
Frontend: image picker with a 2:3 crop box and a live preview inside the chosen template.
•
Backend: multer memory storage, validate type and size, upload to platform/covers, return publicId and url, save
them on the Book.
•
If a writer skips the cover, show a generated placeholder (title on a tinted block, drawn in the frontend) while
coverPublicId is empty.

12.8 What not to copy
Use the same structure and colour family, not the same assets. Do not use Wattpad's logo, illustrations, icons, hero
images, cover images, headline wording or the name "Wattpad" anywhere in your product, and do not hotlink their
images. Layouts, grids and an orange palette are normal design choices; their artwork and branding are not. Draw your
own genre illustrations or use licensed or open icon sets, and use seeded sample books with your own placeholder
covers.
